# Charm 预览页复刻

本项目把 typeui.sh 上 Charm 设计系统的四个预览页——Marketing、Application、
E-commerce 与 Components——复刻为一个零外部依赖、双击即可打开的单文件 HTML，
用于离线查阅这套设计系统中各组件的实际写法、间距与状态。

主交付物是 `charm-preview.html`，体积 710 KB。字体、CSS、四页 DOM 与交互 JS 全部内嵌
在这一个文件里，它既不读取同目录下的其它文件，运行时也不发起网络请求，因此可以单独
拷贝到任意位置使用。页面底部居中有一个悬浮切换器，用来在四页之间切换；初次打开时显示
Marketing 页，若要直接定位到某一页，可以在文件名后附加页面标识，例如
`charm-preview.html#p=ecommerce` 会直接打开 E-commerce 页。

这 710 KB 中，样式表占 219 KB，其中内嵌的 woff2 字体约 131 KB，是 Inter、DM Sans 与
Fragment Mono 三款字体的拉丁子集；四页 DOM 占 472 KB，含 543 个内联 svg 与 23 份下拉
面板；脚本占 19 KB。

同一套构建器还能产出另外七个产物。它们都不纳入版本库，需要时在本地重建，原因见
[入库范围](#入库范围克隆-10-mb中文版本地重建)一节。

| 产物 | 体积 | 内容 |
|---|---|---|
| `charm-preview-cjk.html` | 72.8 MB | 字体替换为思源黑体与更纱黑体，覆盖全量 CJK |
| `charm-preview-cjk-gb.html` | 16.0 MB | 同上，但字形按 GB2312 子集化，收录 6763 个常用汉字 |
| `charm-preview-cjk-gb-zh.html` | 16.0 MB | 设计试验台，在子集版之上叠加设计层与中文文案；一切设计改动都只在这个产物上验证 |
| `charm-preview-cjk-gb-zh-dark.html` | 16.0 MB | 试验台的深色配色版，内容与上一项相同，配色由明亮版按 OKLCH 与 APCA 推算得到，推导过程见[关键决策](#关键决策) |
| `charm-preview-cjk-gb-zh-console.html` | 16.0 MB | 试验台的控制台皮肤版，把深色版的暖炭中性族再锚定为近黑冷中性，并改为方角与扁平；品牌色与状态色逐字节不变 |

## 项目概况

本项目包含四项工作，后三项都建立在第一项之上。第一项是复刻本身，把四个浏览器保存件
整理成可以离线打开的单文件，并补回其中缺失的浮层 DOM。第二项是为复刻结果建立一套自动
检查，用以确认改动没有破坏页面。第三项是中文字体的内嵌与子集化。第四项是在复刻产物之上
叠加设计改动，同时保证复刻层本身不受影响。

| 工作 | 内容 | 代码 |
|---|---|---|
| 复刻 | 保存件的样式依赖外链，弹窗与下拉菜单未被渲染。本项目将外部样式、字体与图标全部内嵌，并按原始编译产物补回缺失的浮层 DOM | `_build_charm.py` 1770 行 |
| 验证 | 六层共 129 项自动检查，末层是合并版与单页版的逐像素比对，不设容差 | `_verify_charm.mjs` 803 行 |
| 中文字体 | 字体内嵌与 GB2312 子集化；等宽字体选用更纱黑体以保证中英混排时的列对齐，并由程序核验 | `_make_cjk_fonts.py` 249 行 |
| 设计分层 | 深色、皮肤、品牌、设计、内容五层叠加在复刻产物之上，由 `--dark`、`--console` 与 `--sim` 选定组合，复刻层逐字节不受影响 | 六个文件共约 2500 行 |

四项工作遵循同一条纪律：凡是自动化的改动，都必须给出可由程序判定的预期，而不依赖目测。
举例来说，某段样式在页面中应当出现三次，这个数字就写死在构建脚本里，实际出现两次或
四次都会使构建立即失败。这样做是为了避免产出一个外观正常、实际已经损坏的文件。全项目
此类断言共 144 处。

构建过程具备确定性，相同的输入产生逐字节相同的输出，全量重建约需 0.2 秒。因此重跑一次
构建再比对产物字节，本身就是一条可靠的回归信号。

## 保存件的局限

四个预览页的浏览器保存件无法直接使用，原因有两层。其一是依赖外部资源：样式来自 3 个
外部 CSS 与 40 多个 Next.js chunk，字体则指向已经失效的外链。其二更为关键，保存下来的
只是首屏的静态快照，modal、drawer、下拉菜单以及 FAQ 的后三个分类在文件中根本不存在
——保存的那一刻 React 尚未渲染它们。因此复刻不只是把资源收进来，还要把这些缺失的
DOM 按原始编译产物重新补回去。

## 构建管线

`_build_charm.py` 用一张 `PageSpec` 表描述四个页面，每一页都经过同一条流水线处理。
`PageSpec` 的字段如下：

```python
@dataclass(frozen=True)
class PageSpec:
    slug, label, title, src_dir, src_html, root_anchor, id_prefix
    clean:    tuple[CleanRule, ...]    # 带 [lo,hi] 命中数断言的正则替换
    restores: tuple[Restore, ...]      # 锚定插入缺失的隐藏态 DOM
    menus:    tuple[MenuSpec, ...]     # 按触发器判别式插回下拉面板
    patch_css, js                      # 该页专属的还原补丁与交互层
    inline_imgs, fix_recharts, extra_css
    expect_class_counts                # 计数预言机：class 出现次数必须完全一致
```

| | clean | restores | menus | 其它 |
|---|---|---|---|---|
| marketing | 3 | 2 | — | `inline_imgs`（11 个 `<img>` → data URI） |
| application | — | 4 | 10 模板 → 21 个触发器 | `fix_recharts` |
| ecommerce | 2 | 2 | 2 | |
| components | 1 | 6 | — | 独有 `1l8ijtal3t07p.css` 全量并入 |

流水线共七步，依次是：截取正文、清洗外链、补回隐藏态 DOM、插回下拉面板、内联图片、
修正 recharts 容器，以及逐个 svg 为其内部 id 添加页前缀。七步之后，构建器收集 class
白名单，按原 `data-precedence` 顺序合并 CSS，最后拼入 `.pv` 外壳。

CSS 的合并顺序不可颠倒，依次为内嵌 `@font-face`、4309 的令牌与 reset、1mf3 按四页并集
筛出的白名单切片（61 KB）、1l8ijtal3t07p 全量，以及外壳补丁。顺序之所以重要，是因为
`.btn:focus-visible` 定义在前者而 `.btn.is-focus` 定义在后者，一旦颠倒就会改变焦点表现。

每一步都带有 `need()` 断言。如果源页面更新导致某个锚点失效，构建会立即报错，而不会
静默产出一个损坏的页面。

## 关键决策

> 本节逐条记录选型理由、否决过的方案与实测数据，供查阅，不必通读。

**合并成一个文件而不是四个。** 内嵌字体有 131 KB，合并之后只需出现一次；若拆成四个
独立文件，这部分就要重复四次。

**切换器必须是 `position:fixed` 浮层，不得占据布局。** 一旦占位，被压缩的那一维就需在四页中逐处补偿：

- 占**顶部**（竖向）要改写 `.ds` / `.page` / `.appshell` 的 `100vh`、`.modal` 的 `max-height`，外加 8 个 fixed 浮层逐个让出 bar 高——这是第一版的做法，可行但补丁量过大。
- 占**侧边**（横向）代价更高：共享 CSS 里有 **21 个宽度断点、0 个高度断点**。纵向缩减 56px 不影响任何断点，横向缩减则使**每一个断点都与真实内容宽度错位**（1440 视口配 200px 栏 → 内容 1240px 却仍套用 `@media (min-width:1280px)` 的排版）。要修只能把 `@media` 全改 `@container`，等于重写 61 KB 第三方 CSS。
- 做成浮层后，外壳补丁只碰 `html/body` 与 `.pv*`，**一条原页面规则都不覆盖**，合并版与单页版因此能做到逐像素相等。

**切换器贴底而非贴顶**同样有实测依据。在 1440×900 视口下滚动至顶部时，页面上方正是
四页各自安放常驻导航的位置，实测结果如下：

| 位置 | marketing | application | ecommerce | components |
|---|---|---|---|---|
| 顶部居中 | 盖住 `Contact` | 盖住搜索框 | **盖住语言选择 + 5 个主导航项** | 无 |
| 底部居中 | 无 | 无 | 无 | 无 |

原站取 `bottom-4 left-1/2`，推测出于同一原因。切换器的深色玻璃样式沿用原站——它是 **typeui.sh 的站点 chrome，不是 Charm 组件**，需一眼可辨其为外壳而非被预览的页面，因此刻意使用字面值而非 Charm 令牌（CSS 注释中已注明，以免后续被误改）。

**每个页面的根节点外必须再包一层 `.pv`。** 四个根节点的 display 取值各不相同，其中
`.page` 与 `.appshell` 是 flex，若直接给它们加 `[hidden]`，会被自身的 display 覆盖而
失效。这层 wrapper 同时还承担另外两个职责：作为每页独立的滚动容器，以及记忆该页的
滚动位置。

**补回的文案一律从 chunk 正则提取，不手抄。** 40 条 FAQ、3 档定价、application 的 5 份列表、12 个月营收——写错一个词不会触发任何告警，手抄的风险不可接受。`expect_class_counts` 再从 DOM 侧补一层计数校验。

**id 改名逐个 `<svg>` 局部进行，全程使用字节级 regex，不引入 HTML parser。** parser 在
重新序列化时会破坏 `<clipPath>`、`<linearGradient>` 这类 SVG 标签名的大小写，引用随之
静默失效。之所以局部改名就已充分，是因为实测发现四页中的 `url(#x)` 引用全部落在定义它
的那个 `<svg>` 内部，跨 svg 引用为 0，svg 之间没有嵌套，且引用形式只有 `fill="url(#x)"`
一种。

**下拉面板不使用 portal**，而是作为触发器的紧邻兄弟内联在原处。这样做有三点好处：
`position:fixed` 不受祖先影响（已核对祖先链上没有 transform、filter 或 contain），面板
随 `.pv[hidden]` 自动隐藏，并且省去了 21 个 `aria-controls` id。需要注意的是，滚动发生
在 `.pv` 与 `.appmain` 上，因此重定位的监听必须设 `capture:true`，否则面板不会跟随滚动。

**21 个触发器通过判别式匹配模板，而不是按序号。** 序号会随 DOM 的细微调整而错位，何况
其中 10 个触发器本就是同一模板在表格各行中的复用。判别式优先取 `aria-label`，没有则取
按钮的纯文本，并做双向断言：既没有触发器匹配落空，也没有模板处于闲置。

**图标生成器先自证。** archive / pencil / trash-2 / log-out 四个图标在快照中从未出现，只能从 chunk 的 `iconNode` 定义生成。为此先取快照里**已渲染**的 6 个图标（user / settings / credit-card / eye / x / ellipsis）作**逐字节对照断言**，确认生成器与 React 的序列化完全一致，再用它补齐那四个。

**表格的选中状态不另存 Set，而是直接从 DOM 中统计 `:checked`。** 这样就不存在第二份
状态，也就无从失去同步。promote 那一列的开关完全由 CSS 的 `:checked` 驱动，不含 JS。

**recharts 图表不缩放的原因不在 viewBox。** `<svg class="recharts-surface">` 本就带有
`viewBox` 与 `width:100%`。真正的原因有两处：ResponsiveContainer 在服务端渲染出了一个
`width:0;height:0;overflow:visible` 的中间层，子元素的 100% 因此等于 0；同时
`.recharts-wrapper` 被写死成了快照当时的像素尺寸。把这两处都改成 100% 之后，图表即可
跟随容器缩放，无需引入 recharts 运行时。

**路由只识别 `#p=<slug>` 这一种形式。** 四页中存在 13 个形如 `#components`、`#overview`
的页内锚点，若直接用裸 slug 作路由就会与它们重名。除 `#p=` 之外的 hash 一律交给浏览器
做页内跳转。切换页面时使用 `replaceState`，不污染后退栈。

**`.hero-pattern` 与 `.shero-pattern` 引用的 `hero-pattern-swirl.svg` 在四个保存件目录
中都不存在。** 处理办法是只删除那一条 `background-image` 声明，保留其 opacity 与 mask。
不自制替代纹理，因为该图属于设计资产，猜测出来的结果比缺失更糟。

**设计上的试验一律不进入复刻层，而是单独分层，只作用于 zh 那几个产物。** 五个复刻产物
的价值在于「与原站一致」这一可验证的性质，像素回归与逐字节比对都以它为前提；设计改动
一旦混入，这些性质就不再成立。因此设计与内容的改动全部落在 zh 产物上，由它承担试验台
的角色。各层的分工如下：

```
_build_charm.py   复刻层   四页 → 五个产物，忠实复刻，不含任何设计改动
_theme_dark.py    深色层   整版配色推导            ┐ 作用于 --dark / --console
_theme_console.py 皮肤层   令牌再锚定 + 镜像同步   ┘ 只作用于 --console
_theme_brand.py   品牌层   锚定主色 + 推导 + 镜像   只作用于 --sim（可叠 --dark）
_ds_zh.py         设计层   令牌 / 色板 / 组件      ┐ 作用于五个 zh 产物
_localize_zh.py   内容层   文案                   ┘
_build_zh.py      编排     cjk-gb 产物 → (深色层 → (皮肤层 | 品牌层深色段)) 或 (品牌层) → 设计层 → (后段) → 内容层
```

层的顺序是设计层在前、内容层在后。这样安排是因为设计层加入的色块标签（`info`、
`warning-soft`）本身就是设计令牌名，理应保持英文，不该被内容层翻译。新增一条设计改动，
做法是在 `_ds_zh.py` 的 `build_layers()` 中添加一个 `Patch`；每个 Patch 都自带命中数
断言，这一约束继承自复刻层。

设计层目前包含四项改动，前三项**由既有规律推得，而非另立一套**：

- **新增蓝色状态色族 info。** 原站只有 success / danger / warning 三族。先量三族既有的
  HSL 关系——strong 一律是 base 的 `L−9`（实测 −7.8 / −9.2 / −10.8），soft 一律落在
  `L≈95`、S 降到 ~68——再照这套关系在 hue 212 上推出
  `#287ee2 / #1a68c1 / #eaf2fb`，另给一个 `info-medium`（danger / warning 有
  medium，success 没有，此处补齐）。新族因此与原三族观感一致。
- **补上 `warning-soft`，状态色板改成一族一行。** `--warning-soft:#fff6df` 这个令牌原本
  就存在，只是原站色板漏了展示，导致 warning 只有 base 与 strong、与 success / danger 的
  三色不齐。现在四族各三色，且每族独占一个网格（容器同宽，各行的列天然对齐），
  不再被 auto-fill 的折行切散。
- **新增「文字颜色」色板。** 原站色板展示了品牌、表面、状态，唯独没有「文字用了哪些
  颜色」。这一块**从产物自己身上数出来**：CSS 里每条 `color:` 声明逐层解开 var() 链求到
  字面值，再加上 SVG `<text>` 的 fill=；按语义分组、组内由深到浅，没有令牌的裸字面值
  标注「无令牌」。CSS 一改色板随之更新，不会出现「文档记 16 种、实际 19 种」的偏差。
- **标题字体栈思源黑体置首。** 原站 `--font-display-stack` 首位是 Circular Std / CircularXX TT，
  商业字体、不随产物分发；中文页上若看的人恰好装了它，标题会拉丁走 Circular、汉字回落思源黑体，
  同一行两套字形。改为 `var(--font-display)`（内嵌的思源黑体）置首，其余后备原序保留，就地改写
  令牌本身。实测五个 zh 产物与改前相比只差这一处令牌与说明块里的一条。

前三项色板改动受两条实现约束。其一，色板中每个 hex 都由 `token_value()` 从产物自身的 CSS
读出后生成，不存在手抄的副本。其二，设计层在出口处断言 `ds__swatch` 与 `ds__chip` 各
26 个，外加文字色板的条数（明亮版 19 条、深色版 22 条），色板若再被改动会立即报错。
此外，令牌注入的位置在 `</style>` 之前、即样式块之内，而不是插在它后面。

⚠ 另有一处发现：原站**已有** `.ds__alert--info` 变体，但它借用的是品牌红
`--ds-brand-soft`——设计系统里有个 info 状态，却因为没有蓝色令牌而套了品牌色。
设计层只补了色族本身，**未改动该变体的样式**；要让它真的变蓝，需要加
`--ds-info-soft` / `--ds-info-fg` 并覆盖那条规则。（`--sim` 产物里品牌色本身就是蓝，
info 族又并入了品牌色阶，该变体因此自然呈蓝、语义也随之正确。）

**深色版并非明亮版的整体减光，而是整版由明亮版推算得到（`_theme_dark.py` → `--dark` 产物）。**
原站没有任何深色定义（三个被引用的 CSS 里 `.dark` / `prefers-color-scheme` /
`[data-theme]` 全部 0 命中），必须从零推一套。推导不在 HSL 里做——HSL 的 L 与感知明度
无关（`#ffa211` 与 `#287ee2` 的 HSL-L 只差 1 个点，OKLab-L 差近 20 个点）；空间用
**OKLCH**（感知均匀、hue-linear，改明度色相不漂），对比度用 **APCA**（W3C 草案 0.1.9，
WCAG 2.x 对深底浅字系统性高估，APCA 是唯一给出可信读数的模型）。核心是「墨即纸」：
深色版的 `--page` 直接锚定明亮版的 `--heading` `#1c1917`，`--heading` 由等 Lc 解出
`#faf3ee`——不取纯白并非取舍偏好，而是模型解出的结果（`#ffffff` on `#1c1917` 的 Lc=106.6 过冲
且落在散光糊边区间，等 Lc 解恰好停在 `#faf3ee`）。三条规则：**面**保相对 page 的
ΔL ×1.30（CIECAM16 暗环绕下感知对比约降 24%）；**线**方向翻转（明亮版边框比面暗、
深色版必须比面亮），ΔL 锚在**各自坐的面**上等量搬运（×1.00：暗环绕 ×1.30 与光渗
×0.77 相抵）；**墨**走等 Lc 移植，并按所坐的面兜底（见下一段）。**APCA 只用于文字**——它是可读性模型不是可辨识模型，
实测拿它定 1px 描边会把 `--border` 推到亮得发白的 `#52514f`。出厂值是评审过的定稿表，
构建期用规则**重算全表**并断言逐通道差 ≤1/255（OKLab 逆变换在 8-bit 取整边界上，
不同实现会向不同方向翻，钉量化步才可复现）；真正钉死的是 **APCA 多座面审计**：
每个墨与状态字在它所坐的每一种面上都不低于明亮版，且至少一面取等。唯一的刻意妥协是品牌前景：严格等 Lc 会把
`--fg-brand` 的彩度从 0.171 掉到 0.104（珊瑚红退成鲭鱼粉），设彩度下限 C≥0.13 取
`#f4897f`，拿 Lc 换彩度（67.5→53.7），依据 Helmholtz–Kohlrausch——高彩度前景的视觉
明度高于其亮度，APCA 不建模此项。映射必须是「角色×上下文」**三级**而非一张值表，
反例都是产物里数出来的：`#fff` 同时是 `--card`（变深）与 `--white`（保白）；`#a8a29e`
同时是 `--border-strong`（线）与 `--fg-disabled`（墨）；`#1c1917` 在色板上是 heading、
在商品颜色选择器上是「Black」这个商品色（恒等）；`#ffe9c1` 在 `:root` 是 warning-medium、
在 ecommerce 插画里是暖光（恒等——插画只暗化纸与结构，不动彩色内容，「浅底上的淡黄」
于是变成「暗底上的暖光」）。var() 引用还有一处延伸：`--brand-soft` 被图表当**线**用
（次要系列、圆环轨道、图例点）时，深色 soft 是与卡片同明度的徽章底面，绘制后即不可见，
这几处换成按线规则单独推导的 `#4b2d2b`（ΔL 与明亮版逐位对齐）。外壳切换器翻成**亮玻璃**
——这不是推翻「深色玻璃一眼可辨」的不变量，是守住它的**本意**：外壳与被预览页面永远
反相，浅色页配深壳、深色页配亮壳。国旗 SVG 与外壳原段整段挖出保护、映射完原样放回；
body 映射是单趟合并正则——映射的输出值（如 `#1c1917`）同时也是输入键，多趟会把输出再
当输入二次映射。最强的回归信号：深色层不触及明亮路径，`python3 _build_zh.py` 重建的明亮版
与改动前**逐字节相同**（已用 `cmp` 实测）。

**深色版的文字在它所坐的每一种底色上都不低于明亮版，这是由渲染审计逼出来的规则（`_audit_contrast.py`）。**
深色层原先只在 page 上等 Lc 移植墨，令牌层面的审计也只看 page，全部通过。但交付打包前做了一次
**逐元素渲染审计**——headless Chrome 打开明暗两版的四页，对每个含文字的元素取计算后的前景色、
沿祖先链（SVG 用 `elementsFromPoint` 取下方图形栈）叠出实际背景，算 APCA Lc，再把明暗两版的同一段
文字对齐比较——1378 段里 328 段在深色下更难读。归因后是四类问题，令牌层都看不见：
① **面的方向翻转**：明亮版里卡片（`#fff`）是对比最好的面，深色版里卡片（`#24201e`）比 page 亮、
反而最差，卡片上的次要文字掉了约 6 Lc、状态字最多掉 10；② **反色药丸**：组件页 tooltip 是「墨底
白字」，墨翻亮后成了白字配近白底，Lc 0；③ **基色当文字**：基色恒等是为按钮面与图形定的，危险菜单项、
评价区大引号、插画里 5 处文字直接拿品牌 / 危险基色写字，深色下 Lc 掉到 27–34；④ **插画里的彩色
小字**：头像缩写是「同色 0.15 圆上的同色字」，深色下同色圆叠在深卡片上，紫色字 Lc 20.7。
对应的修法都写成了规则而不是逐处打补丁：
墨与状态字改为**多座面兜底**——先在基准面（墨是 page，状态字是各自的 soft）上等 Lc，再对它实际所坐的
每一种面（page、card、card-soft、control-fill、band、hover-fill；状态字是 soft、page、card）兜底：
深色 Lc 不得低于明亮版同一面，封顶 Lc 90（APCA 正文推荐值，再高在深底上只增加光渗），不够就提亮；
越出色域时降彩度、保色相，不再裁通道（原先 danger-strong 因裁通道偏了 4°）。一个值管不住方向相反的
两种面，只能取「处处不低于」，所以基准面上会比明亮版略高（`--body` 在 page 上 81.7→87.6），这是
不退化的代价，审计要求至少一面取等以防无端提亮。结果 body / body-subtle / fg-disabled 与四族
strong 都由 card 约束、提亮一档，heading 不变。tooltip 改用新令牌 `--tooltip`（值即图表提示的反色面
`#38322e`，皮肤层可再锚定）；基色当文字一律换同族前景档（品牌 → `--fg-brand`，危险 →
`--danger-strong`，插画里随文的图标同理）；插画头像缩写按墨处理，在深色下实际所坐的底上等 Lc。
（非文字的同类问题也一并处理：`.select` 的下拉箭头是 data URI 里的 SVG，颜色按 URL 编码写死为
`%2379716b`，深色下 Lc 只有 26，残留检查只认 `#79716b` 所以漏了；现换为深色 body-subtle，
残留检查同时查 `%23rrggbb` 写法。）
改完再审：三个深色产物各 1360 余段文字，**退化 0 段**；只剩品牌前景按约定例外列出（拿 Lc 换彩度，
要求不低于定稿值 −1.5）。这道审计已固化为 `python3 _audit_contrast.py`，有退化即 exit 1；拿改动前的
深色产物跑，它报出全部 328 段，证明它确实能抓住这类问题。

**换皮肤不重新推导，而是把已审计的关系整体再锚定一次（`_theme_console.py` → `--console`
产物）。** 深色层是「整版重推导」：从明亮版出发，逐族解出面 / 线 / 墨。皮肤层的输入却已经
是一套审计过的关系，重推一遍等于把那些审计推翻重来。所以它只做两件事：**面 / 线 / 抬升
整体平移**——`--page` 从暖炭 `#1c1917` 移到近黑 `#0e0e0e`（ΔL=−0.0524），彩度一律归零
（C=0，与暖炭的 56° 色相带彻底脱钩）；整体平移意味着深色层审计过的**全部 ΔL 关系原样保留**，
面的层级序、线的方向翻转、hover-fill 的夹层位置都不用重新论证。**墨则不平移**，在冷 page
上按明亮版的 Lc 目标重解——平移会把对比度一起平移掉，而墨的判据从来是感知对比不是
明度差（`--body` 若跟着平移会掉到 Lc 76）。品牌与四族状态色**逐字节不变**，恒等断言逐条在场：更换的是外壳，不是品牌。实测冷底
只让它们变好——`--fg-brand` 的 Lc 53.7→54.7、`--fg-brand-strong` 67.2→68.1，四族 soft
由「与 card 几乎等明度」（深色版 ΔL≈0.002，正是 `#4b2d2b` 那条专用线值存在的理由）变成
明确浮在 card 之上（ΔL≈0.05）。这两条均已写成断言，而非事后描述。墨的重解同样按深色层的
多座面规则：冷 page 上等 Lc，card 等所坐的面不低于明亮版（`--body` 为 `#dfdfdf`，由 card 约束）；
继承来的状态字在更暗的冷面上只会更清楚，也逐面断言。`--tooltip` 随中性面一起平移为冷值。

皮肤层的边界不是「只动 `:root`」，而是「**令牌 + 令牌在 body 里的镜像**」。components 页把
8 个中性色块（chip 的内联 style + hex 标签成对）与 7 个圆角演示块（`border-radius:` + px 标签）
烙进了 body——那是令牌的字面镜像。令牌改而镜像不改，色板即与实际取值不符，违反「色板自证、
无手抄副本」这条硬性不变量（深色层的 `CHIP_MAP` 成对改并断言 `chip==label` 是先例）。除
这 15 处外 body 一律不碰。圆角演示块必须**按令牌名锚整个单元**、绝不按值多趟替换：`r-xs`
的旧值 `4px` 恰是 `r-xl` 的新值，值键碰撞会把刚写好的值再当输入二次映射——与深色层「输出值
同时是输入键」是同一课。`--r-full:9999px` 不动，它的 40 处引用是圆点、头像、开关滑块，
必须保圆（代价见[已知差异](#与原页面的已知差异)）。

皮肤层**夹在深色层与设计层之间**是唯一可行位置：设计层的 `token_value()` 与
`text_color_census()` 都是「首次声明胜」，皮肤层先行，设计层随后生成的色板天然自证冷值；
放到设计层之后，色板显示的就是刚被覆盖掉的旧值。同理全部改写都是**就地 replace**，
在 `</style>` 前追加覆盖块会让浏览器认后者、census 认前者，渲染与色板静默分家。
gone 扫描收窄到**两个令牌 `:root` 块之内**——外壳 `EXTRA_CSS` 的亮玻璃与 `.ds` 链的死回退中，
暖值是合法存在的（前者是站点 chrome，后者不可达），全域扫描必然产生假阳性。回归信号同深色层：
明亮版与 `--dark` 两条路径重建后与改动前**逐字节相同**（`cmp` 实测过）。

**换品牌色：主色由设计指定，其余七档按职能从珊瑚红推出（`_theme_brand.py` → `--sim` 产物）。**
起因是试验台要承载仿真模型界面，而原站品牌色有一处硬伤：`--brand #e4544b` 与
`--danger #e5484d` 在 OKLCH 里色相只差 4°、明度只差 0.011——「运行」按钮与「发散/报错」
同色。目标选蓝（CAE 软件的通行配色）。否决的备选是石油青（204°）：它恰在 success 与 info
之间色相环最大空档的中点，单看最干净，但与图表的 `--teal`（185°）只差 19°，application 页
New leads / Returning、Infants / Toddlers 这些相邻系列会分不清，要连带给 `--teal` 换色，
牵动 14 处图表元素。

第一版是纯推导：色相取 info 的 255°，每档「等 Lc 转色相」，得到 `#4188df`。随后设计方指定
了参考按钮的蓝，于是改为**锚定**：`brand` 钉为该值，其余七档围绕它推。锚点取的是 DevTools 里
的计算值 `rgb(26 102 255)` = **`#1a66ff`**（OKLCH 0.566 / 0.238 / 262.2，与 IBM Carbon 的
blue-60 几乎同色；DevTools 自己给出的 `oklch(0.57 0.24 262.24)` 与本项目的 OKLab 实现吻合）。
**不从截图取色**：Mac 截图嵌着显示器 ICC，直接读像素会偏——同一个按钮曾被读成 `#3264f6`，
按嵌入的配置换算回 sRGB 才是 `#1a65ff`（差 1/255）；拿本页已知色值验证过这条换算，误差同级。

锚点比等 Lc 推出的蓝深且艳——白字 Lc 77.7（珊瑚 69.2），C/Cmax 1.00（珊瑚 0.73，蓝通道 255，
正在 sRGB 色域边界上）——这使「每档等 Lc」不再成立：`.btn--primary` 是 light → brand → medium
的竖向渐变（hover 往深端移），若只换 brand，medium 的 Lc 75.9 会比 brand 还浅，渐变明暗倒挂。
规则因此按职能分开：

- **按钮面四档**：白字 Lc 相对珊瑚原档**整体平移** +8.6（= 锚点与珊瑚 brand 的差），档间 Lc
  差原样保留——与皮肤层「整体平移、关系不动」同一思路。brand 一档由此解回 `#1966ff`，与锚点差
  1/255，这本身就是自洽断言。
- **前景两档**（fg-brand / -strong）：**不平移**，解 L 使在 page 上的 Lc 等于珊瑚原档（67.5 /
  74.9）。前景的判据是文字可读，不跟按钮的明暗走；结果 `--fg-brand #2268f8` 与锚点几乎重合，
  即链接色≈按钮色。
- **彩度**：珊瑚各档相对珊瑚 brand 的 C 比例换算到锚点的 C，超出色域则截到 Cmax（本锚点下
  brand-light / -strong 落在边界上）。不用相对彩度 C/Cmax 放大——蓝色相在深端的色域边界逼近
  sRGB 蓝原色，试算锚点 `#3264f6` 时 `brand-strong` 被推到刺眼的 `#0e00ee`。
- **浅色调两档**：L 与绝对 C 不变，只转色相。白色附近的 Cmax 随色相剧烈变化（青色系的色域
  尖峰在高 L 处），保相对彩度会让浅底刺眼——试算石油青时 brand-soft 得到 `#71fbfb`。

结果：`#1a66ff / #3e7eff / #0354eb / #0043c3 / #d5e3fd / #ebf2fd`，前景 `#2268f8 / #1a59d7`。
审计：求解的 6 对 Lc 对上目标（|Δ|≤0.2），按钮四档白字 Lc 严格递增，未求解的 4 对派生组合
不退化。另有两条断言的**量法**在锚定时一并改正，不是放宽（触发它们的是 `#3264f6` 那一版）：
其一，各档色相一致性原先按角度（≤3°），但 `brand-softer` 的 C 不到 0.02，8-bit 取整就能让它
抖近 4°；改为「与理想点在 ab 平面上的距离 ≤0.002」，即一个量化步（实测单通道 ±1 位移
0.0011–0.0017）。其二，图表并列系列原先按色相角 ≥45°；但色相角忽略彩度——两个低彩度色差
45° 也分不清，两个高彩度色差 40° 却很分明——改用 OKLab ΔE ≥0.15（JND≈0.02，约 7 个 JND）。
`#1a66ff` 与 `--purple` 色相差 44°、ΔE 0.171，与 `--teal` ΔE 0.241；原站三系列两两是
0.27–0.28，这一项新蓝比珊瑚红弱，截图目检饼图与堆叠柱仍分得清。

设计层新增的 info 蓝（255°）与锚点只差 7°，两族并存只会是两种几乎一样的蓝，所以 **info 族
并入品牌色阶**（IBM Carbon 的做法）。档位恰好对得上：info-soft 与 brand-softer 都是 L .958，
info-medium 与 brand-soft 都是 L .913，这两条写成了断言；info-strong 并入 fg-brand-strong
（不是 brand-strong：它的职能是 soft 底上的文字，深色版里 brand-strong 是恒等的按钮深蓝，只有
fg-brand-strong 两版都是文字色），在 info-soft 上的 Lc 由 68.8 升到 71.5。并入必须在设计层
**之后**做（info 是设计层注入的），
品牌令牌的改写则必须在设计层**之前**做（「首次声明胜」，文字色板才自证蓝值）——于是品牌层
与深色层同构，分主段与后段。边界与皮肤层相同，是「令牌 + 令牌在 body 里的镜像」：`:root`
的 8 个品牌令牌，加上 components 页烙进 body 的 18 处字面值（品牌色阶 6 对 chip/label 按
令牌名锚整个单元、头图色条 6 块整串替换）；`--elevation-3` 与 `--focus-ring` 经 var()
自动跟随，中性色、状态三族、点缀色一个字节不动。

**配套深色版（`--sim --dark`）不改深色层，而是让它按珊瑚跑完、再换品牌族。** 深色层的品牌
定稿值全从珊瑚推出，断言里也钉着珊瑚原值；把它参数化成「任意品牌」要动几十处，且 `--dark`
产物的逐字节不变就得重新论证。所以深色层原样跑，品牌层深色段 `apply_dark` 随后把深色珊瑚
的品牌族换成「深色层同一套规则作用于明亮蓝」的结果——深色层只为此把三条规则抽成可复用的
函数与常量（`dark_soft()` / `dark_series()` / `BRAND_FG_FLOOR`），重算断言不变。它占的是
皮肤层那个槽位（深色层之后、设计层之前），理由也相同：「首次声明胜」，色板才自证蓝值。
换的范围是：基色四档（深色层规则是基色恒等，故与明亮蓝同值）；soft / softer 直接调
`dark_soft()` 得 `#152036 / #151e2c`；图表次要系列线调 `dark_series()` 得 `#2a364e / #222b3a`
（命中数从深色层自己的 `var_patches()` 数出）；焦点环取深色层那条声明换品牌色；`.ds` 回退
链里深色层写进的 brand-softer 字面值；以及与明亮版相同的 18 处 body 镜像（深色层对它们恒等）。

唯一需要判断的是品牌前景。严格等 Lc 会把 fg-brand 的彩度从 0.226 压到 0.095（`#a0c1ff`
那种淡紫蓝）——与珊瑚当年「退成鲭鱼粉」是同一个问题。深色层对珊瑚的定稿是拿 Lc 换彩度
（53.7 / 67.2），依据 Helmholtz–Kohlrausch；蓝是该效应最强的色相，理由对蓝更成立，所以
沿用同一组 Lc 目标（读 `BRAND_FG_LC`，不另定数），C 取明亮版、超出色域截到 Cmax。结果
fg-brand `#78a7ff`（C 0.138，过 0.13 下限；与 Carbon 深色主题的 blue-40 `#78a9ff` 几乎同色），
fg-brand-strong `#9ec1ff`（C 0.096）。后者低于珊瑚的 0.10 下限，但那是该明度上 sRGB 的
色域上限，所以断言写成「不低于下限，或已取到色域上限」。info 族明暗两版同一映射（令牌
别名）；深色下 info 文字/底的 Lc 由 77.2 降到 66.8——它跟着品牌前景的取舍走（品牌前景是深色
对比度唯一的约定例外，用户确认保留），底线因此定为珊瑚深色版品牌的同一对（66.7），不是 info 原来那一对。

插画里 5 处品牌字与组件页 tooltip 两个问题，已在深色层按规则修复（见上文「深色版的文字在它所坐的
每一种底色上都不低于明亮版」一段），蓝色深色版自动跟随。

**交付给业务网页实现者的是一个包，不是两个 HTML（`_pack_sim.py` → `handoff/`）。** 实现者要的
不是「照着看」，而是能直接引用的东西：`tokens/theme.css`（明暗两套 CSS 变量，深色版同时挂在
`[data-theme="dark"]` 与 `prefers-color-scheme` 上，不设属性即跟随系统）、`tokens/tokens.json`、
从产物 `@font-face` 原样解出的 8 个 woff2 与 `fonts.css`，外加风格说明与两个模版。包内没有手抄
的数值：令牌、字号与间距梯度、对比度表、组件 CSS 摘录（45 条，按选择器从模版原文取，断言顶层
恰好一条，媒体查询里的同名规则一并列出）、深色版令牌之外的差异清单（两个模版的 CSS 逐条
比对得出）都由脚本生成；人写的只有令牌用途说明，且与真实令牌**双向断言**——缺说明或多说明
都会让打包失败。模版里是字面值、业务页又需要统一引用的五个值补成了令牌（`series-soft` /
`series-softer` / `scrim`，以及明亮版没有令牌的 `hover-fill` / `tooltip`），在说明里标「补充」。字体许可：
子集化裁掉了 name 表的许可证记录（更纱原件里本来也没有），许可名与上游地址按本 README 的
下载表写在脚本里，版权与版本仍从字体自身读。zip 用固定时间戳，同输入逐字节同输出（实测两次
打包 sha256 相同）。`handoff/` 不入库；风格说明另发布为页面，用的是去掉文档外壳的同一份内容
（`handoff/_page/`）。

风格说明末尾的**组件样例**是模版组件页的原样内容，不是另画的示意。明暗两个模版各取一份：DOM 按
`<div>` 嵌套层数截出 `.ds` 容器（去掉带来源站点署名的头图与分区导航，断言 8 个分区、38 个组件块），
样式表在外壳补丁处截断、去掉字体声明与令牌块、`html`/`body` 规则改挂 `:host`，一起放进**声明式
影子 DOM**——模版的全局规则（`*` 重置、h1–h6、button）与说明页自己的样式互不渗透，而令牌作为
CSS 自定义属性会穿过影子边界从文档的 `theme.css` 继承，主题切换在样例里同样生效；随主题只显示
对应那份。组件页自己的交互脚本原样取出（断言明暗两版一致、只用到 `document.querySelector` /
`getElementById` / `addEventListener` 三个接口），给它一个指向影子根的替身 `document` 运行，标签页、
下拉、手风琴、弹窗、抽屉、步进器、滑块都能点。一致性是测出来的：样例与模版组件页逐元素比对 17 项
计算样式（颜色、背景、渐变、边框、圆角、字体、字号、字重、行高、内边距、阴影等），明亮 1024 个、
深色 1026 个元素，0 处不一致。

回归信号同前：另外三个 zh 产物重建后与改动前**逐字节相同**（`cmp` 实测过），其中也包括
深色层的 `lch_cmax` 与三条规则的抽取。`--sim` 不与 `--console` 叠加：皮肤层的品牌恒等
断言按珊瑚写，蓝色控制台版要另做。

**替换字体只需改动三个令牌的值，不触及任何一条页面 CSS 规则。** 四页的字体栈写作
`var(--font-inter), "Inter", ui-sans-serif, …`，内嵌字体占据的永远是第一顺位的那个
令牌，因此 `FontPack` 只需给出 `--font-inter`、`--font-display` 与
`--font-fragment-mono` 三个值即可。
`--fonts=cjk` 因此不引入布局风险，拉丁版产物亦逐字节不变（已实测）。

**等宽字体不随正文一并换为 Noto Sans SC，而是单独使用更纱黑体。** Noto Sans SC 的拉丁
部分是比例字体，用它充当等宽会使 `.ds__file`、`.stat-tile__value` 这些位置失去列对齐。
更纱黑体（Sarasa Mono SC）把汉字宽度做成拉丁的整二倍，中英混排时同样不破列。
`_make_cjk_fonts.py` 中有断言核验这一点——拉丁 500 units、汉字 1000 units——不成立即
拒绝出包。

**中文版提供两档，在字形覆盖面与文件体积之间取舍。** 全量 CJK 版 72.8 MB，任何汉字都能
显示；GB2312 子集版 16.0 MB，收录 6763 个常用汉字与 682 个符号，生僻字、繁体字与日文
假名会回退到系统字体。
两版的英文渲染实测等价（逐像素比对：最大单通道色差 1/255，落在 6 个色块的圆角上，
按本项目像素回归自己的判据 ΣRGB>6 即为零差异）。

子集的字符集不手抄「常用字表」，而是**枚举 GB2312 的全部合法双字节码位**解出来
（必然 7445 个，不多不少），再并上拉丁与标点各区，最后并上**拉丁版产物里出现过的
每一个字符**——最后这一项是硬性要求：四页正文为英文，漏掉任何一个在用字符都会使产物
当场退化为系统字体。实测由此补回 3 个字符。

两版都只内嵌页面真正用到的 8 个字面（Noto 5 + 更纱 3），并在 `@font-face` 上直接声明
字重区间把匹配钉死：Noto 无 600/800、更纱无 500，全靠区间落到真实字面，不触发合成粗体。
子集化之后会**重新量一遍等宽指标**（拉丁 500 / 汉字 1000），subset 若改动了 advance width
即就地报错——这条断言保证列对齐不会在子集化这一步丢失。

**puppeteer-core 安装在本目录之外。** 本目录是一个自包含的可分发单元，不应出现
`node_modules`，因此验证脚本改用 `createRequire` 加载依赖，它能够识别 `NODE_PATH`。

## 与原页面的已知差异

1. 标题字体使用 **DM Sans**。原设计首选的是商业字体 Circular Std，而规范本身即指定 DM Sans 作为它的免费替代。
2. modal / drawer / 下拉菜单等浮层在快照里并不存在（React 未渲染），按各页的编译产物 chunk 逐字还原；原实现靠卸载节点隐藏，本复刻改用 `[hidden]` 切换。
3. 全部交互由原生 JS 重写，状态只存放在 DOM 属性上，不另设一份 JS 状态。
4. 每个 `<svg>` 内部的 id 都加了页前缀。**⚠ 这一并修正了原页面的一处缺陷**：E-commerce 页的 `chBg1` / `chBg7` 各被定义两次，导致其中 2 个商品图取到了其它元素的渐变。改名后各自独立，因此这两张图与原站存在可见色差——属修正，非回归。
5. `hero-pattern-swirl.svg` 不在保存件中，因此引用它的那条 `background-image` 被删除，详见[关键决策](#关键决策)。
6. application 页的 recharts 容器已修复为跟随外层容器缩放，详见[关键决策](#关键决策)。
以上 6 条对**所有产物**成立，它们构成复刻本身的边界。

设计上的改动（补 `warning-soft`、新增蓝色状态色族 `info`、文字色板）**只存在于
`charm-preview-cjk-gb-zh.html` 与其深色版、控制台皮肤版这三个试验台产物**，其余产物是
忠实复刻，不含任何设计改动；分层与理由见[关键决策](#关键决策)。深色版另有三条自身的差异：明亮位图
（marketing 的 11 张头像与照片）像素未动、只加了一条非破坏性压暗滤镜
`brightness(.92) saturate(.96)`（Material / Apple 深色规范的通行做法）；面积渐变的
顶部 stop-opacity 统一 ×4/3（同一 alpha 在暗环绕下感知更弱，属补偿而非额外处理）；
四个浮层遮罩统一为 `#000000b3`（明亮版四处各不相同）。

控制台皮肤版继承深色版的全部差异，另有四条自身的差异：

1. **插画与图表里的字面色仍是暖炭**——纸面 `#14110f`、网格线 `#2c2826`、图表提示药丸
   `#38322e`、次要系列线 `#4b2d2b` 等（组件页 tooltip 的底是令牌 `--tooltip`，已随壳变冷），都是深色层直接写进 body 的值，令牌层面无法触及；
   在冷黑 UI 里呈极轻微暖调（C≤0.01）。它们不在皮肤层的边界内（边界是「令牌 + 令牌的
   body 镜像」），若要改动，需另开一层 body 映射，属独立的工作。
2. **文字色板从 22 条增至 25 条、「无令牌」从 5 条增至 9 条**——这不是设计债，而是分层的
   忠实呈现：上面那些 body 字面值属于深色层，令牌变冷之后它们不再溯源到任何令牌，色板如实
   把它们标成「无令牌」；外壳的 `#1c1917` 也随之失去「碰巧等于 `--page`」这个标注。
   这两个数字在构建期钉死（`_theme_console.CENSUS_TOTAL/ADHOC`），偏移即报错。
3. **药丸按钮与胶囊 chip 保持圆角**——`--r-full:9999px` 不改动，其 40 处引用中含圆点、
   头像与开关滑块，必须保圆。方角只落在 `--r-xs`…`--r-xxxl` 那 40 处引用上。
4. **底部切换器保持深色层的亮玻璃与暖色字面**——它是站点外壳不是被预览的组件，
   「一眼可辨这是外壳」的不变量优先于皮肤统一。

需要 Chrome/Edge 119+、Safari 16.4+、Firefox 128+（用到 `color-mix()`、`rgb(from …)` 与 `:has()`）。

## 把设计要素移植到已有界面

这套设计可以从不同深度取用：最轻的做法是只复制设计变量，稍重一些可以连同组件的 HTML

页面上，便于直接对照：

| Actions | 按钮的变体 / 尺寸 / 状态、图标按钮、按钮组、下拉菜单 |
| Forms | 输入框、文本域、下拉选择、数字步进、验证码、文件拖放、滑块、时间选择 |

### 设计变量

整套视觉规则收敛为 60 个 CSS 变量，集中在文件开头的单个 `:root` 块里，总共 1.6 KB。
把这一段复制进自己的样式表，页面就获得了与预览页相同的视觉基准。用下面这条命令可以
把它取出来：

```bash
grep -o ':root{[^}]*}' charm-preview.html | head -1 | tr ';' '\n'
```

这 60 个变量按职责分为十组：

| 组 | 个数 | 举例 | 职责 |
|---|---|---|---|
| 文字色 | 6 | `--heading` `--body` `--body-subtle` `--fg-disabled` | 标题 / 正文 / 次要 / 禁用，深浅梯度已排定 |
| 背景与表面 | 6 | `--page` `--card` `--card-soft` `--control-fill` | 页面底 / 卡片 / 浅卡片 / 输入框底，层级已排定 |
| 品牌色 | 6 | `--brand` `--brand-strong` `--brand-soft` | 主色及深浅变体 |
| 状态色 | 12 | `--success` `--danger` `--warning` 三族，每族 3–5 个 | 每族含实色、深色与淡底 |
| 点缀色 | 7 | `--purple` `--indigo` `--teal` … | 图表配色与标签分类 |
| 边框 | 5 | `--border-subtle` → `--border-strong` 四档，外加 `--border-on-band` | 分隔线、卡片边、强调边；末项专供彩色条带 |
| 圆角 | 8 | `--r-xs`(4px) 至 `--r-xl`(24px)，外加 `--r-full` | 一套梯度，`--r-full` 为圆形专用 |
| 阴影 | 4 | `--elevation-1/2/3`、`--focus-ring` | 抬升三档与聚焦光环 |
| 字体 | 3 | 正文 / 标题 / 等宽 | 见下 |
| 其它 | 3 | `--white`、`--container`(1280px)、`--section-y`(112px) | 容器最大宽度、大节上下留白 |

取用方式即普通 CSS 变量：

```css
.my-button {
  background: var(--brand);
  color: var(--white);
  border-radius: var(--r-md);
  box-shadow: var(--elevation-1);
}
.my-button:focus-visible { box-shadow: var(--focus-ring); }
```

`--brand` 这一族的六个值决定了全站按钮、链接与聚焦光环的主色，只要替换这一族，整体
配色就随之改变，不必逐处修改组件样式。

### 深色配色

深色配色不能靠把明亮值等比压暗得到。同一组对比度数值在深色背景上的实际可读性低于浅色
背景，直接压暗只会得到一套读起来偏淡的界面。本项目的深色值是按感知明度逐项推算出来的，
并对八组前景与背景做过等对比核对。完整的对照表位于
[`_theme_dark.py` 的 `EXPECTED`](_theme_dark.py#L176)，每个变量一行，摘录如下：

```
              明亮       深色
--page        #f7f7f5 → #1c1917
--card        #fff    → #24201e
--heading     #1c1917 → #faf3ee
--body        #57534e → #e1d7cf
--border      #e7e6e5 → #363230
```

其中有两条规律值得直接沿用。一是深色版的标题不取纯白而取 `#faf3ee`，因为纯白在深色
背景上过亮，边缘还会发糊。二是边框的明暗方向相对明亮版翻转：明亮版的边框比它所在的
面更深，深色版则必须比所在的面更浅，否则线条会在背景中消失。

完整效果可以在 `charm-preview-cjk-gb-zh-dark.html` 中看到，该产物需要在本地重建，
步骤见[入库范围](#入库范围克隆-10-mb中文版本地重建)一节。

### 字体

字体同样由变量决定，一共三个，因此替换字体不需要改动任何一条页面样式：

| 变量 | 用途 | 本项目取值 | 获取 |
|---|---|---|---|
| `--font-sans-stack` | 正文 | Inter | [Google Fonts](https://fonts.google.com/specimen/Inter) |
| `--font-display-stack` | 标题 | DM Sans | [Google Fonts](https://fonts.google.com/specimen/DM+Sans) |
| `--font-mono-stack` | 等宽 | Fragment Mono | [Google Fonts](https://fonts.google.com/specimen/Fragment+Mono) |

三者均为 OFL。产物内嵌的是它们的拉丁子集，合计 131 KB，已随 `_charm_fonts.json` 入库，
重建拉丁版无需另行下载字体。

换中文有一处需要注意：等宽不应随正文一并换为思源黑体，其拉丁部分是比例字体，
作等宽使用会破坏代码与数字的列对齐。本项目正文与标题用思源黑体
[Noto Sans SC](https://github.com/notofonts/noto-cjk/releases/tag/Sans2.004)，
等宽用更纱黑体 [Sarasa Mono SC](https://github.com/be5invis/Sarasa-Gothic/releases/tag/v1.0.36)，
后者汉字宽度为拉丁的整二倍，中英混排不破列。两套均为 OFL，
版本、下载资产与转换步骤见[重建中文版](#重建中文版)。

### 组件 HTML 与交互

组件的 HTML 可以直接复制，连同对应的 CSS 规则一并取走，但有两点边界需要先说明。

第一，产物内的组件 CSS 约 61 KB，它是按四个页面实际用到的 class 筛选出来的子集，
并非完整的设计系统，因此页面上未曾出现的组件可能缺少样式。第二，下拉、弹窗、标签页
这些交互是本项目用原生 JS 重写的，所有状态都存放在 DOM 属性上，例如 `hidden` 与
`aria-selected`，不依赖任何框架，可以整段取用。

### 移植时的注意事项

以下四点是本项目实测遇到过的问题，取用这套设计时同样会遇到。

**悬浮控件不要占据布局。** 这套 CSS 里有 21 个宽度断点，却没有任何高度断点。若某个
常驻控件占去一截横向空间，每一个断点都会与真实内容宽度错位；占去纵向空间则几乎没有
影响。因此常驻控件宜做成不占布局的浮层。

**改用方角时不要连 `--r-full` 一起改。** 这个变量的 40 处引用中包含圆点、头像与开关
滑块，它们必须保持圆形。

**变量在 DOM 中的镜像需要同步修改。** 组件目录页把 8 个色块与 7 个圆角演示块的值直接
写进了 HTML，如果只改变量而不改这些值，设计规范页显示的就是旧值。

**浏览器需要 Chrome/Edge 119+、Safari 16.4+ 或 Firefox 128+**，因为页面用到了
`color-mix()`、`rgb(from …)` 与 `:has()`。

### 不适合沿用的部分

把字体以 base64 内嵌进 HTML，这个做法在中文场景下代价过高。拉丁字体只有 131 KB，
内嵌很划算；换成中文字体后，全量版本会使产物膨胀到 72.8 MB，即便按 GB2312 子集化
也仍有 16 MB。中文项目更适合外链字体，或者在此基础上进一步子集化。

### 工程做法

如果要迁移的是工程做法本身，例如把某个页面固化成单文件，或是在既有产物之上叠加设计
改动而不破坏原件，那么下面四条最具参考价值。

**每一条自动改动都应附带命中次数断言。** 批量替换真正的风险不在于报错，而在于它命中
了 0 次、或是远超预期的次数，却仍然静默地执行完毕。把预期次数写死，出入即失败。

**文案应从原始编译产物中机械提取，不要手抄。** 手抄时写错一个词，不会触发任何告警。

**改写 HTML 应使用文本替换，不要引入 HTML 解析库。** 解析库在重新序列化时会破坏 SVG
中 `clipPath`、`linearGradient` 一类标签名的大小写，引用随之静默失效。

**设计改动应独立分层，不要并入忠实复刻的那一层。** 复刻层的全部价值在于「与原版一致」
这一可验证的性质，掺入设计改动后它就不再成立。本项目的检验方式是：改动设计层之后重建
明亮版，结果必须与改动前逐字节相同。

复刻另一站点时，`_build_charm.py` 的 1770 行中约 1070 行与具体站点无关（管线、规则类、
外壳、共享交互层），约 700 行为四个页面各自的人工补丁；结构见[构建管线](#构建管线)。

## 入库范围：克隆 10 MB，中文版本地重建

仓库收了拉丁版产物与全部构建输入，但**中文字体原件（287 MB）与中文版七个产物都不入库**。

不入库并非因其次要，而是 git 存储它们的代价与收益不成比例：

- 体积的 **96% 是内嵌字体的 base64**——二进制、且已压缩过，git 既不 diff 也不增量存储，
  每存一次即是一份全量；
- 它们**频繁重建**。尤其是 `charm-preview-cjk-gb-zh.html` 这个设计试验台，每做一次设计
  实验即重新生成；若纳入跟踪，每次提交都会向历史再压入一份 12 MB，**且永久留存**，
  十次实验即 120 MB，且无法删除——除非重写历史；
- 重建成本很低：备齐字体原件后，两条命令即可完成。

两种方案的代价对比：三个中文产物入库时 `.git` 为 354 MB、克隆约 80 MB；移出后 `.git` 1.2 MB、
克隆约 10 MB。源码相同，同样能产出全部产物。

另有一点：`charm-preview-cjk.html` 单文件 72.8 MB，会触发 GitHub 的 50 MB 警告线。
Git LFS 可以解决这一条，但会给克隆方引入 git-lfs 依赖，且网页 Download ZIP 只能取得指针
文件——对一个以「单文件可直接使用」为目标的项目并不合适，故未采用。

汇总：

| | 克隆后能否重建 | 缺少的输入 |
|---|---|---|
| `charm-preview.html` / `charm-components.html` | **能**，`python3 _build_charm.py --all` 即可 | — |
| 中文版七个产物（`charm-preview-cjk*.html`） | 不能，七者均**不入库**，需自备字体后重建 | 两套中文字体原件 |

拉丁版可重建这一条经过实测：将三个脚本、四个 `_files/` 目录与 `_charm_fonts.json`
复制到空目录模拟新克隆并执行 `--all`，产出与仓库已提交的版本逐字节一致。

### 重建中文版

**第一步，下载字体原件。** 两套中文字体都不入库（合计 288 MB，其中真正用到的 8 个
字面约 102 MB），需自行下载。目录名与文件名必须与下面一致——`_make_cjk_fonts.py`
按字面量路径查找，缺哪个就报哪个的错，不会静默跳过：

```
NotoSansCJK-Woff2/                 思源黑体 SC，woff2，仅需这 5 个字重
    NotoSansSC-Thin.woff2  Regular  Medium  Bold  Black
SarasaMonoSC-TTF-1.0.36/           等距更纱黑体 SC，TTF，仅需这 3 个字重
    SarasaMonoSC-Regular.ttf  SemiBold  Bold
```

下载地址与本项目所用版本（版本号读自字体 name 表）：

| 字体 | 版本 | 下载 | 许可 |
|---|---|---|---|
| Noto Sans SC | 2.004 | [noto-cjk 的 Sans2.004 release](https://github.com/notofonts/noto-cjk/releases/tag/Sans2.004)，取资产 `18_NotoSansSC.zip`（47.8 MB） | OFL |
| 等距更纱黑体 SC | 1.0.36 | [Sarasa-Gothic 的 v1.0.36 release](https://github.com/be5invis/Sarasa-Gothic/releases/tag/v1.0.36)，取资产 `SarasaMonoSC-TTF-1.0.36.7z`（62.7 MB） | OFL |

两套字体都采用 OFL 许可，可以自由再分发；本仓库不予收录仅仅是出于体积考虑，与许可无关。

**思源需自行转成 woff2。** `18_NotoSansSC.zip` 内是 7 个 `.otf`（Thin / Light /
DemiLight / Regular / Medium / Bold / Black，族名正是 `Noto Sans SC`），而脚本要的是
woff2。用构建字体包本就依赖的 fontTools 转换，只需其中 5 个：

```bash
mkdir -p NotoSansCJK-Woff2
python3 - <<'EOF'
from fontTools.ttLib import TTFont
for w in ("Thin", "Regular", "Medium", "Bold", "Black"):
    f = TTFont(f"NotoSansSC-{w}.otf"); f.flavor = "woff2"
    f.save(f"NotoSansCJK-Woff2/NotoSansSC-{w}.woff2")
EOF
```

实测这 5 个字重合计约需 1 分 40 秒，时间主要花在 brotli 压缩上，产出文件在 5.0 至
6.2 MB 之间。Light 与 DemiLight 两个字重用不到，可以不转。

⚠ 不要改从 [Google Fonts 的 Noto Sans SC](https://fonts.google.com/noto/specimen/Noto+Sans+SC)
取。那是另一支可变字体构建，字重集合与文件命名都与上表不同（没有 DemiLight），
不能直接顶替；noto-cjk 仓库里的全量 CJK 字体则叫 `Noto Sans CJK SC`、文件名形如
`NotoSansCJKsc-Regular.otf`，同样不是这里要的那一支。认准 `18_NotoSansSC.zip`
（等价于仓库内的 `Sans/SubsetOTF/SC/`）。

**更纱黑体的分发包是 `.7z` 格式**，在 macOS 上需先安装解压工具（`brew install p7zip`），
再执行 `7z x SarasaMonoSC-TTF-1.0.36.7z`。包内含 10 个字面，即 5 个字重的直体与斜体，
其中只有 Regular、SemiBold 与 Bold 三个会被用到。另需注意选取带 hinting 的那一份，
而不是文件名中含 Unhinted 的版本。

**第二步，生成字体包。** 全量约 2 分钟（要把 3 个 24 MB 的 TTF 转成 woff2），
子集约 45 秒。两个包互不依赖，只要中文版就只跑对应那一条：

```bash
python3 _make_cjk_fonts.py            # → _charm_fonts_cjk.json     72 MB
python3 _make_cjk_fonts.py --gb2312   # → _charm_fonts_cjk_gb.json  15 MB
```

子集那条会读取 `charm-preview.html` 以取得「产物中在用的字符」，因此**需先有拉丁版产物**
（克隆后即存在；若已删除，先执行一次 `python3 _build_charm.py`）。

**第三步，构建。**

```bash
python3 _build_charm.py --fonts=cjk      # → charm-preview-cjk.html      72.8 MB
python3 _build_charm.py --fonts=cjk-gb   # → charm-preview-cjk-gb.html   16.0 MB
python3 _build_zh.py                     # → charm-preview-cjk-gb-zh.html 16.0 MB（设计试验台）
python3 _build_zh.py --dark              # → charm-preview-cjk-gb-zh-dark.html 16.0 MB（深色版）
python3 _build_zh.py --console           # → charm-preview-cjk-gb-zh-console.html 16.0 MB（控制台皮肤版）
python3 _build_zh.py --sim               # → charm-preview-cjk-gb-zh-sim.html 16.0 MB（工程蓝品牌版）
python3 _build_zh.py --sim --dark        # → charm-preview-cjk-gb-zh-sim-dark.html 16.0 MB（工程蓝深色版）
```

后五条需先有 `charm-preview-cjk-gb.html`：设计试验台是在子集版之上再经设计层与内容层，
深色版在设计层之前先经深色层，皮肤版则在深色层与设计层之间另插一层，工程蓝版在设计层
之前先经品牌层，工程蓝深色版在深色层之后先经品牌层深色段（分层说明见[关键决策](#关键决策)）。

**关于字节可复现**：脚本对 `NotoSansCJK-Woff2/` 里的 woff2 是原样收下、不再转换，
但上游只发 OTF，这道转换落在了使用者手上，转出的字节取决于本机的 fontTools 与 brotli
版本——实测上面那条转换命令的产物与本项目所用文件在 Regular 上差 120 字节。更纱那 3 个
同样要经 fontTools + brotli 转换与子集化。所以中文产物**不保证跨工具链逐字节复现**
（本项目用的是 fontTools 4.61.1），也不入库，没有「仓库版本」可供 `cmp`——真要确认字体取对了，
就比对**拉丁版**：`python3 _build_charm.py --all` 后 `charm-preview.html` 必须与仓库里的
逐字节一致（它不含中文字体，与工具链版本无关，是干净的对照）。

### 单独导出中文字体

`python3 _make_cjk_fonts.py --export` 将包内的更纱黑体解回独立 `.woff2`
（输出至 `SarasaMonoSC-Woff2/`，全量 3 个字重共 25 MB），供其它项目直接以 `@font-face` 引用；
加 `--gb2312` 则导出子集版（约 1.5 MB/字重）。这一步仅做 base64 解码，不重跑转换。
